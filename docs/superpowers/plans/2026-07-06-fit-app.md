# Fit App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a local day-organized exercise-tracking web app (spec: `docs/spec.md`) end to end: Postgres schema + seed, Express API, React UI, verified in a real browser.

**Architecture:** Two packages in one repo. `server/` is an Express 5 + TypeScript API over Postgres with plain SQL — one route file, one query file, dates handled as plain `YYYY-MM-DD` strings throughout. `web/` is a Vite + React + TypeScript SPA with a single day-page view; all mutations are optimistic upserts against `/api/logs`. The server pre-sorts exercises LRU per section for the requested date; the client freezes that order for the life of the page view.

**Tech Stack:** Node 22, Express 5, pg, TypeScript, Vitest + Supertest, Vite, React 18. Ports: web 5177, api 8003. DBs: `fit`, `fit_test`.

  weight NUMERIC(6,1),
  note TEXT,
  UNIQUE (exercise_id, performed_on)
);
CREATE INDEX IF NOT EXISTS idx_logs_date ON logs (performed_on);

  - `lastPerformed` = latest completed log strictly **before** the requested date; null when never.
  - LRU order: never-performed first, then oldest `lastPerformed` first.
  - `lastWeight` = latest non-null weight on logs **≤** requested date.
  - `PUT /api/logs {exerciseId, date}` creates row `completed:false`; second PUT with `{completed:true}` updates only that field; PUT with `{weight: 185}` sets weight; fields not sent are untouched.
  - `DELETE /api/logs/:exerciseId/:date` removes the row; deleting a missing row is a 204 no-op.
  - `POST /api/exercises {name, category, isWeighted}` — existing category reused; new category appended at max(position)+1.
  - Validation: bad date → 400; unknown exerciseId on PUT → 404.

- [ ] **Step 3:** Implement `queries.ts`:

```sql
-- getDay($1 = date): one query for the page
SELECT c.id cat_id, c.name cat_name, c.position,
       e.id, e.name, e.is_weighted,
       lp.last_performed,
       lw.last_weight,
       l.completed, l.weight, l.note, (l.id IS NOT NULL) AS has_log
FROM exercises e
JOIN categories c ON c.id = e.category_id
LEFT JOIN logs l ON l.exercise_id = e.id AND l.performed_on = $1
LEFT JOIN LATERAL (SELECT max(performed_on) last_performed FROM logs
                   WHERE exercise_id = e.id AND completed AND performed_on < $1) lp ON true
LEFT JOIN LATERAL (SELECT weight last_weight FROM logs
                   WHERE exercise_id = e.id AND weight IS NOT NULL AND performed_on <= $1
                   ORDER BY performed_on DESC LIMIT 1) lw ON true
ORDER BY c.position, lp.last_performed ASC NULLS FIRST, e.position, e.name;
```

Upsert: `INSERT ... ON CONFLICT (exercise_id, performed_on) DO UPDATE SET completed = COALESCE($3, logs.completed), ...` with COALESCE-per-field so partial updates work (send explicit `null` handling for weight/note clears via dedicated sentinel: passing `weight: null` clears — implement by building the SET list in JS from provided keys instead of COALESCE where clearing must be possible).
